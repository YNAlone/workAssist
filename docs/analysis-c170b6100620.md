# orchestra 功能总结

> 分支：`refactor/agent-platform`  
> 分析范围：`agent_platform/` 新内核 + `feishu_claude_automation/` 旧链路兼容层  
> 分析性质：只读代码梳理，未修改任何业务代码，未调用飞书 API。

---

## 1. 概述

`Orchestra` 是 `refactor/agent-platform` 分支上引入的**多 Agent 平台编排内核**（项目经理角色）。它的核心职责是：接收用户目标 → 创建 Job → 由 Planner 拆分为 PlatformTask → 通过 TaskBus 分发给具体 Agent Executor → 聚合回调结果并更新 Job 状态。

当前处于 **M1 骨架阶段**：

- 已落地 `agent_platform` 包、PostgreSQL 持久化、`AgentRegistry`、`TaskBus`、`Orchestra`、`Planner`。
- `CodeAgentExecutor` 已可用，包装原有 GitHub Actions 调度链路。
- `DocAgentExecutor` 仅为 M2 占位桩，直接抛出 `DispatchError`。
- 旧单体 `Orchestrator`（`feishu_claude_automation/orchestrator.py`）仍然保留，用于 `/feishu/events`、`/feishu/actions`、`/callbacks/runner` 等兼容路径。

## 2. 核心模块与调用链路

### 2.1 核心文件与职责

| 文件 | 核心类/函数 | 职责 |
|------|-------------|------|
| `src/agent_platform/orchestra.py` | `Orchestra` | 创建 Job、调用 Planner、派发 Task、查询 Job 聚合结果 |
| `src/agent_platform/planner.py` | `Planner` | M1 启发式规划：根据显式 `agent_id` 或 goal/inputs 推断 Agent |

| `src/agent_platform/models.py` | `Job`、`PlatformTask`、`AgentSpec`、`AgentKind` | 领域模型与状态枚举 |
| `src/agent_platform/store.py` | `PlatformStore` | SQLAlchemy 持久化（jobs / tasks / audit_logs） |
| `src/agent_platform/app.py` | `build_platform_app` | 组装 Registry、Store、Bus、Orchestra、Executor 实例 |
| `src/agents/code_agent.py` | `CodeAgentExecutor` | 包装 GitHub Actions workflow_dispatch |

| `src/feishu_claude_automation/orchestrator.py` | `Orchestrator` | 旧单体编排器（自然语言会话、审批、GitHub 调度、飞书卡片） |
| `config/agents.json` | — | Agent 注册表静态配置 |

### 2.2 调用链路（新平台 API 路径）

```text
POST /v1/jobs
  └─ AutomationHandler.do_POST
      └─ platform.orchestra.create_and_dispatch(...)
          ├─ Job.create + PlatformStore.save_job
          ├─ Planner.plan_tasks(...) → list[PlatformTask]
          ├─ PlatformStore.save_job(plan, task_ids)
          ├─ for task in tasks:
          │     PlatformStore.save_task(task)
          │     TaskBus.dispatch_task(task)
          │         ├─ AgentRegistry.get(task.agent_id) → AgentSpec
          │         ├─ executors[agent.executor] → Executor
          │         ├─ executor.can_handle(task)
          │         └─ executor.dispatch(task)
          │             └─ CodeAgentExecutor.dispatch
          │                 └─ GitHubClient.dispatch_workflow
          │                     └─ GitHub Actions API workflow_dispatch
          └─ TaskBus.refresh_job_status(job_id)

GitHub Actions Runner 完成/失败后
  └─ POST /callbacks/runner (或 /v1/tasks/callback)
      └─ platform.bus.apply_callback(payload)
          ├─ PlatformStore.require_task(task_id)
          ├─ AgentRegistry.get(task.agent_id)
          ├─ executors[agent.executor].on_callback(payload)
          │   └─ CodeAgentExecutor.on_callback
          │       └─ 更新 task.status / result / error
          ├─ PlatformStore.save_task(updated)
          └─ TaskBus.refresh_job_status(job_id)
```

### 2.3 双轨兼容（旧链路路径）

`server.py` 在 `/callbacks/runner` 处做兼容兜底：

```text
/callbacks/runner
  ├─ 若 platform_app 启用且 apply_callback 成功 → 走新 TaskBus
  └─ 否则 → Orchestrator.handle_runner_callback → 旧 JSON 任务存储 + 飞书通知
```

## 3. Agent 的注册与发现机制

### 3.1 注册：静态 JSON 配置

Agent 定义集中存放在 `config/agents.json`。`AgentRegistry.from_file()` 在启动时一次性加载。

```python
@classmethod
def from_file(cls, path: str | Path) -> AgentRegistry:
    data = json.loads(Path(path).read_text(encoding="utf-8"))
    agents: list[AgentSpec] = []
    for item in data.get("agents", []):
        agents.append(
            AgentSpec(
                id=item["id"],
                kind=AgentKind(item["kind"]),
                display_name=item.get("display_name", item["id"]),

                allowed_tools=list(item.get("allowed_tools") or []),
                policy_ref=item.get("policy_ref", ""),
            )
        )
    return cls(agents)
```

### 3.2 运行时索引

`AgentRegistry.__init__` 把 agents 列表转成字典 `self._agents = {agent.id: agent}`（`src/agent_platform/registry.py:11-12`）。

发现接口：

- `get(agent_id: str) -> AgentSpec`：按 ID 查找，未找到抛 `AgentNotFoundError`（`src/agent_platform/registry.py:32-36`）。
- `list() -> list[AgentSpec]`：返回全部 Agent（`src/agent_platform/registry.py:38-39`）。
- `by_kind(kind: AgentKind) -> list[AgentSpec]`：按 kind 过滤（`src/agent_platform/registry.py:41-42`）。

### 3.3 Executor 绑定

`Executor` 不是由 Registry 直接实例化，而是在 `build_platform_app()` 中手工装配到 `executors` 字典（`src/agent_platform/app.py:57-64`）：

```python
code_executor = CodeAgentExecutor(settings, store, policy=policy)
doc_executor = DocAgentExecutor()
executors = {
    "code": code_executor,
    "github_actions": code_executor,
    "doc": doc_executor,
    "feishu_mcp": doc_executor,
}
bus = TaskBus(store, registry, executors)
```

绑定规则：

- Agent 的 `executor` 字段决定使用哪个 Executor 实例。
- `TaskBus.dispatch_task` 先用 `registry.get(task.agent_id)` 得到 `AgentSpec`，再用 `self.executors.get(agent.id) or self.executors.get(agent.executor)` 查找 Executor（`src/agent_platform/bus.py:33-34`）。
- 这意味着既可以按 `agent.id` 直接绑定，也可以按 `agent.executor` 绑定，提供一定灵活性。

## 4. Orchestrator 调度逻辑

### 4.1 入口：Orchestra.create_and_dispatch

`src/agent_platform/orchestra.py:20-69`：

```python
def create_and_dispatch(
    self,
    *,
    goal: str,
    requester_id: str = "",
    chat_id: str = "",
    agent_id: str = "",
    inputs: dict[str, Any] | None = None,
    auto_dispatch: bool = True,
) -> dict[str, Any]:
```

流程：

1. 校验 `goal` 非空，否则抛 `ValidationError`（`orchestra.py:30-32`）。
2. 创建 `Job` 并保存，状态设为 `PLANNED`，写入审计（`orchestra.py:34-37`）。
3. 调用 `Planner.plan_tasks(...)` 得到 Task 列表（`orchestra.py:39-46`）。
4. 把 Task 列表摘要写回 `job.plan`，`job.task_ids` 保存（`orchestra.py:47-51`）。
5. 遍历 tasks：保存每个 task；若 `auto_dispatch=True`，调用 `bus.dispatch_task(task)`（`orchestra.py:53-58`）。
6. 调用 `bus.refresh_job_status(job.id)`；若已派发且状态仍为 `PLANNED`，则提升为 `RUNNING`（`orchestra.py:60-64`）。
7. 返回 `{job, tasks}`。

### 4.2 Planner：M1 启发式路由

`src/agent_platform/planner.py:9-52`：

```python
class Planner:
    DOC_HINTS = ("文档", "docx", "飞书文档", "wiki", "readme.md 之外的文档", "云文档")
    CODE_HINTS = ("仓库", "分支", "pr", "pull request", "github", "代码", "repo")
```

`plan_tasks` 逻辑：

1. 优先使用调用方显式传入的 `preferred_agent`（`planner.py:26`）。
2. 未指定时，调用 `_infer_agent(goal, inputs)`：
   - 若 `inputs` 含 `doc_url` / `doc_token` → `doc`（`planner.py:38-39`）。
   - 若 `inputs` 含 `repo` / `base_branch` → `code`（`planner.py:40-41`）。
   - 否则对 goal 文本做关键词打分，doc 分高则 `doc`，否则 `code`（`planner.py:44-47`）。
   - 若 goal 中出现 `owner/repo` 形式的仓库标识 → `code`（`planner.py:50-51`）。
3. 当前 M1 始终返回**单个 Task**：`return [task]`（`planner.py:35`）。

因此，M1 尚未实现多 Agent 并行拆分，只是把请求路由到 `code` 或 `doc` 单一 Agent。

### 4.3 TaskBus 派发

`src/agent_platform/bus.py:32-64`：

```python
def dispatch_task(self, task: PlatformTask) -> PlatformTask:
    agent = self.registry.get(task.agent_id)
    executor = self.executors.get(agent.id) or self.executors.get(agent.executor)
    if executor is None or not executor.can_handle(task):
        raise DispatchError(f"no executor for agent={task.agent_id} executor={agent.executor}")

    task.status = PlatformTaskStatus.DISPATCHED
    task.updated_at = utc_now()
    self.store.save_task(task)
    self.store.append_audit(...)
    try:
        executor.dispatch(task)
    except Exception as exc:
        task.status = PlatformTaskStatus.FAILED
        task.error = str(exc)
        ...
        self.refresh_job_status(task.job_id)
        raise DispatchError(str(exc)) from exc
    return task
```

要点：

- 派发前先 persist 为 `DISPATCHED`，写审计 `task.dispatched`。
- 调用 `executor.dispatch(task)`；若抛异常，捕获后把任务置为 `FAILED`，保存并刷新 Job 状态，再抛 `DispatchError`。
- 无队列优先级机制：M1 是 immediate dispatch。

### 4.4 Job 状态汇总

`TaskBus.refresh_job_status`（`src/agent_platform/bus.py:90-111`）：

```python
def refresh_job_status(self, job_id: str) -> Job:
    ...
    if statuses == {PlatformTaskStatus.SUCCEEDED}:
        job.status = JobStatus.DONE
    elif statuses == {PlatformTaskStatus.FAILED}:
        job.status = JobStatus.FAILED
    elif PlatformTaskStatus.FAILED in statuses and PlatformTaskStatus.SUCCEEDED in statuses:
        job.status = JobStatus.PARTIAL
    elif any(s in statuses for s in (PlatformTaskStatus.RUNNING, PlatformTaskStatus.DISPATCHED, PlatformTaskStatus.QUEUED)):
        job.status = JobStatus.RUNNING
    else:
        job.status = JobStatus.RUNNING
```

状态机简单聚合：全成功→DONE、全失败→FAILED、混合→PARTIAL、仍有进行中的任务→RUNNING。

### 5.3 CodeAgentExecutor 的参数转换

`CodeAgentExecutor` 把 `PlatformTask` 转成旧版 `Task`/`TaskRequest`，从而复用现有 GitHub 调度链路。

`src/agents/code_agent.py:27-58`：

```python
def _to_legacy_task(self, task: PlatformTask) -> Task:
    inputs = task.inputs
    repo = str(inputs.get("repo") or "").strip()
    if repo:
        repo = self.policy.resolve_repo(repo) or repo
    prompt = str(inputs.get("prompt") or task.goal)
    base_branch = str(inputs.get("base_branch") or "").strip()
    work_branch = str(inputs.get("work_branch") or f"ai/dev-{task.id}")
    mode_raw = str(inputs.get("mode") or TaskMode.CREATE.value)
    mode = TaskMode(mode_raw) if mode_raw in {m.value for m in TaskMode} else TaskMode.CREATE

    request = TaskRequest(
        repo=repo,
        prompt=prompt,
        base_branch=base_branch,
        requester_id=task.requester_id,
        chat_id=task.chat_id,
        session_id=task.job_id,
        mode=mode,
    )
    ...
    legacy = Task.from_request(request, work_branch=work_branch, risk_level=RiskLevel.LOW)
    legacy.id = task.id
    legacy.status = TaskStatus.DISPATCHED
    return legacy
```

要点：

- `PlatformTask.id` 被复用为 legacy `Task.id`，保证 GitHub Actions callback 的 `job_id` 能与 platform task 对齐。
- `task.goal` 作为默认 prompt；`inputs.prompt` 可覆盖。
- `inputs.repo`、`inputs.base_branch`、`inputs.work_branch`、`inputs.mode` 是代码任务的关键字段。

### 6.1 Executor 协议

### 6.2 CodeAgentExecutor 触发

`src/agents/code_agent.py:60-66`：

```python
def dispatch(self, task: PlatformTask) -> None:
    legacy = self._to_legacy_task(task)
    result = self.github.dispatch_workflow(legacy)
    task.status = PlatformTaskStatus.RUNNING
    task.result = {"dispatch": result, "work_branch": legacy.work_branch, "repo": legacy.repo}
```

2. 调用 `GitHubClient.dispatch_workflow()` 触发 GitHub Actions `workflow_dispatch`。

因此 Code Agent 的触发是**异步触发**：Orchestra 只负责把 workflow 发出去，真正执行在 GitHub Actions Runner 中。

### 6.4 同步/异步说明

- **异步**：当前 Code Agent 走 GitHub Actions，Orchestra 发出 dispatch 后立即返回，Runner 执行完成后通过 HTTP callback 回写结果。
- **同步潜力**：若未来 Executor 在进程内直接调用 MCP/LLM，则可在 `dispatch()` 内阻塞完成并直接写 `task.status = SUCCEEDED`。当前接口未限定同步或异步。

## 7. 回调与结果处理

### 7.1 回调入口

Runner 向 `callback_url` 发 POST。服务端有两个端点接收：

- `POST /callbacks/runner`（兼容旧链路，也是 GitHub workflow 中硬编码的地址）。
- `POST /v1/tasks/callback`（新平台专用）。

`src/feishu_claude_automation/server.py:106-119` 处理 `/callbacks/runner`：


### 7.2 TaskBus.apply_callback

`src/agent_platform/bus.py:66-88`：

```python
def apply_callback(self, payload: dict) -> PlatformTask:
    task_id = str(payload.get("job_id") or payload.get("task_id") or "")
    if not task_id:
        raise DispatchError("callback missing job_id/task_id")

    task = self.store.require_task(task_id)
    agent = self.registry.get(task.agent_id)
    executor = self.executors.get(agent.id) or self.executors.get(agent.executor)
    if executor is None:
        raise DispatchError(f"no executor for callback agent={task.agent_id}")

    updated = executor.on_callback(payload)
    updated.updated_at = utc_now()
    self.store.save_task(updated)
    self.store.append_audit(...)
    self.refresh_job_status(updated.job_id)
    return updated
```

流程：解析 task_id → 加载 task 与 agent → 找到 executor → 执行 `on_callback` → 保存 → 刷新 Job 状态。

### 7.3 CodeAgentExecutor.on_callback

`src/agents/code_agent.py:68-92`：

```python
def on_callback(self, payload: dict[str, Any]) -> PlatformTask:
    task_id = str(payload.get("job_id") or payload.get("task_id") or "")
    task = self.store.require_task(task_id)
    status = str(payload.get("status") or "").lower()

    if status in {"running", "dispatched"}:
        task.status = PlatformTaskStatus.RUNNING
    elif status in {"pr_created", "succeeded", "success", "completed"}:
        task.status = PlatformTaskStatus.SUCCEEDED
        task.result = {
            **task.result,
            "pr_url": payload.get("pr_url", ""),
            "summary": payload.get("summary", ""),
            "commit_sha": payload.get("commit_sha", ""),
        }
        task.error = ""
    elif status in {"failed", "error", "cancelled"}:
        task.status = PlatformTaskStatus.FAILED
        task.error = str(payload.get("error") or "workflow failed")
    else:
        task.status = PlatformTaskStatus.RUNNING
        task.result = {**task.result, "raw_status": status}

    task.updated_at = utc_now()
    return task
```

状态映射：

| Runner 上报 status | PlatformTaskStatus | 说明 |
|--------------------|--------------------|------|
| running / dispatched | RUNNING | 心跳/进度 |
| pr_created / succeeded / success / completed | SUCCEEDED | 完成（含无 PR 的分析报告完成） |
| failed / error / cancelled | FAILED | 失败 |
| 其他 | RUNNING | 未知状态保守视为运行中 |

结果字段写入 `task.result`：pr_url、summary、commit_sha；错误写入 `task.error`。

### 7.4 旧 Orchestrator 的结果处理与报告投递

当回退到旧链路时，`Orchestrator.handle_runner_callback`（`src/feishu_claude_automation/orchestrator.py:180-226`）会：

1. 更新 legacy `Task` 的 pr_url、summary、commit_sha、error。
2. 根据 status 把任务置为 RUNNING / PR_CREATED / FAILED。
3. 若回调携带 `report_markdown` 或 `report_url`，调用 `_deliver_report_to_feishu`：
   - 将 Markdown 导入为飞书云文档。

## 8. 异常处理与重试

### 8.1 派发异常

`TaskBus.dispatch_task`（`src/agent_platform/bus.py:48-63`）捕获 `executor.dispatch(task)` 的所有异常：

```python
try:
    executor.dispatch(task)
except Exception as exc:
    task.status = PlatformTaskStatus.FAILED
    task.error = str(exc)
    task.updated_at = utc_now()
    self.store.save_task(task)
    self.store.append_audit(event="task.dispatch_failed", ...)
    self.refresh_job_status(task.job_id)
    raise DispatchError(str(exc)) from exc
```

异常被记录到 task.error、audit_logs，任务状态置 FAILED，Job 状态刷新，最后向上抛 `DispatchError`。

### 8.2 回调异常

`TaskBus.apply_callback` 未对 `executor.on_callback` 做 try/except 包装（`src/agent_platform/bus.py:77-87`）。若 Executor 解析失败，异常会直接上抛到 HTTP 层，由 `server.py` 的异常处理统一返回 400/500。

### 8.3 参数校验异常

- `Orchestra.create_and_dispatch`：goal 为空抛 `ValidationError`（`src/agent_platform/orchestra.py:30-32`）。
- `CodeAgentExecutor._to_legacy_task`：repo/base_branch 为空抛 `ValueError`（`src/agents/code_agent.py:48-51`）；`policy.validate_request` 校验仓库白名单、基线分支、受保护分支等。
- `AgentRegistry.get`：未找到 Agent 抛 `AgentNotFoundError`。
- `PlatformStore.require_job/require_task`：未找到抛 `JobNotFoundError`/`TaskNotFoundError`。

### 8.4 超时

- GitHub API 请求超时 30 秒：`src/feishu_claude_automation/github.py:28` `urllib.request.urlopen(request, timeout=30)`。
- Runner 回调超时 30 秒：`templates/github/feishu-claude.yml:322` `urllib.request.urlopen(req, timeout=30)`。
- 无任务级执行超时：GitHub Actions 自身有默认 6 小时作业超时，Orchestra 不主动监控。

### 8.5 重试与降级

- **当前无自动重试机制**：`TaskBus` 与 Executor 均未实现失败重试、指数退避或死信队列。
- **降级路径**：`/callbacks/runner` 在新平台解析失败时回退到旧 `Orchestrator`（`src/feishu_claude_automation/server.py:113-117`）。
- **M2 计划**：DocAgent 需要 UAT OAuth 与 MCP 客户端，当前仅抛错占位。

## 11. 结论与后续关注点

1. **M1 仍是单任务编排**：`Planner` 目前只返回单个 `PlatformTask`，尚未实现设计文档中的多 Agent 并行拆分。
2. **Agent 发现依赖静态配置**：新增 Agent 需要同时修改 `config/agents.json` 和 `build_platform_app()` 中的 `executors` 字典。
3. **结果回传是异步回调模型**：Code Agent 通过 GitHub Actions `workflow_dispatch` + HTTP callback 完成闭环，Orchestra 本身不阻塞等待执行结果。
4. **异常处理已有基础，但缺少重试**：派发失败会落库为 FAILED 并抛错，但无自动重试、无死信队列、无执行超时监控。
5. **DocAgent 未实现**：M2 需要补齐 UAT OAuth、飞书 MCP 客户端以及对应的 `DocAgentExecutor.dispatch/on_callback`。
6. **双轨兼容会在未来收敛**：`/callbacks/runner` 目前优先走新平台、失败回退旧链路；随着平台稳定，应逐步移除旧 `Orchestrator` 的调度职责。
